# skill 草案：ChatLuna 预设提示词撰写与修改（2026-10-23，第 1 版）

> 目标：**下次改预设能照着做**。只覆盖「注入层 / 规则层 / 关键词层」，人设层不动。
> 依据：`prompt-skill-research-2026-10-23.md` 的证据卡（ChatLuna 文档 + 源码 +
> SillyTavern 经验 + Anthropic 教程）。

## 触发条件

出现下面任一情况时用这个 skill：

- 用户描述「她应该是这样」「这句要改」→ 判断落在哪一层（见「分层」）；
- 对话测试发现问题：出戏、误触发、该触发没触发、太长/重复；
- 要新增/调整世界书条目、关键词、`loreBooksPrompt`、`### 角色扮演强制规则`；
- 升级 chatluna 后要重核命中/注入行为。

## 硬边界（先看，违反就停）

| 层 | 内容 | 能不能改 |
|---|---|---|
| 人设层 | 性格、说话方式、行为规则、对话示例、基本信息 | **不能改**；用户没说不动，就只记录不动手 |
| 规则层 | `### 角色扮演强制规则`、`config.loreBooksPrompt` | 可改，需写依据 |
| 关键词层 | `keywords`、`scanDepth`、`caseSensitive`、条目切分、顺序 | 可改，需写依据 |
| 产物层 | `bin/exports/`、`dev/` 日志 | 只生成、不手改 |

人设核心要动的，先出回执说明改什么/为什么/依据，**等用户确认**。

## 输入

1. 用户原话（必须原文引用，不改写、不润色）；
2. 当前源文件：`bin/requirements/穗乃香_预设/穗乃香_预设.yml`、`bin/requirements/世界书/*.yml`；
3. 最近一次对话日志（`dev/dialogues/logs/*.jsonl`）与命中计划（`lores_match.py` 输出）；
4. `validate_preset.js` / `audit_world_book.js` 的输出。

## 步骤

0. **读基线**：`git status` 必须干净；跑一次 `node src/validate_preset.js` 确认现有产物 0 errors；
   若已有对话日志，先看一遍，把问题写成一句话（现象 + 用例编号 + 期望）。
1. **分层判定**：把要改的点放进上表四层之一；落不进「规则/关键词」的，停手回执。
2. **写变更单**（先写后改，一句话一条）：
   - 改哪个文件哪一段；
   - 依据（用户原话 / 日志里的哪一轮 / 哪条调研结论）；
   - 预期指标（该命中的命中率、误触发数、出戏次数、平均长度）；
   - 失败判据（什么情况算退步，直接回滚）。
3. **小步改**：一次只改一类；保留原措辞与版块顺序；探索性大改先复制到 `dev/` 试。
4. **集成（按日期标签，不覆盖）**：
   ```bash
   node src/integrate_preset.js 10.23-r1     # 新标签，别复用旧目录
   ```
5. **校验**：`node src/validate_preset.js 10.23-r1` 必须 **0 errors**；warning 逐条看。
6. **对话测试**（在 Koishi 主机上，busy 感知的客户端）：
   ```bash
   node dev/dialogues/dialog_client.cjs --inst <实例> \
     --cases dev/dialogues/cases-baseline.json --out <日志.jsonl>
   ```
   再用 `dev/dialogues/lores_match.py --preset <新产物> --log <日志>` 算命中计划。
7. **对比**：同一批用例，与上一轮日志逐条对比；指标退步就 `git checkout -- <文件>` 回滚，
   产物目录留着不动。
8. **记录**：`dev/dialogues/2026-10-2x-rN.md` 写「现象 → 改动（哪一层）→ 复测结果 → 结论」；
   提交信息写清改了哪一段、依据是什么。

## 检查项（改完逐条打勾）

- [ ] YAML 禁区：源文件无行首 `#`；`content: |-` 后无非缩进行（`validate_preset.js` 致命项）
- [ ] 关键词：无单字（例外「渚」）；无高频日常词（未来/日向/小雪/一花/blue/向阳/真夏/珊瑚/心音/永久…）
- [ ] 大小写：英文关键词默认**区分大小写**（源码 `caseSensitive` 默认 true）；要不区分就写
      `caseSensitive: false`
- [ ] 顺序与预算：单条内容长度 ÷ 1.5 ≈ token；**超预算的条目会挤掉后面的条目**（源码 `break`），
      所以高频条目要短、大条目靠后
- [ ] 扫描窗口：`scanDepth: 2` = 当前消息 + 最近 1 条（含机器人回复），别假设只扫用户输入
- [ ] 常驻条目：`constant: true` 目前保持 0 个；要恢复只留最核心定义（≤4K 字符）
- [ ] 递归：`recursiveScan: false`
- [ ] 注入模板：`loreBooksPrompt` 只能有一个 `{input}` 变量；措辞声明「这是你早已知道的事」，
      不写「你必须……」
- [ ] 重复关键词 / 重复 world_lores 段（validate 会报）
- [ ] 人设层零 diff：`git diff -- bin/requirements/穗乃香_预设/穗乃香_预设.yml` 里没有人设段改动

## 指标（一轮至少看四个）

| 指标 | 算法 | 目标 |
|---|---|---|
| 命中符合率 | 与 `lores_match.py` 的命中计划对比（应命中/不应命中） | 应命中全中、误触发 0 |
| 出戏次数 | 回复里是否出现「设定/资料/世界书/刚知道」或 AI 自指 | 0 |
| 角色一致性 | 多轮里称呼、语气、`欺负人` 等口头反应是否稳定 | 人工判读，记「稳/飘」 |
| 长度与延迟 | 每轮字数、`latencyMs` | 不因改动暴涨 |

## 产出物

- 源文件 diff（逐条可读）；
- 新产物目录 `bin/exports/presets/10.23-rN/`（旧目录不动）；
- 对话日志 `dev/dialogues/logs/<日期>-rN.jsonl`；
- 当轮记录 `dev/dialogues/<日期>-rN.md`。

## 反模式

- 整段重写、顺手重构人设措辞；
- 给测试用例特判、为过测试改期望值、凑回复；
- 复用/覆盖旧产物目录；手抄 `.bak` 当备份；
- 没测就改、改完不 validate；
- 用「业界都这么做」当依据（每条改动要能指到日志或源码）。

## 已知边界

- 命中计划是**离线复算**（按源码语义），token 是估算；真实注入还要看预算与 `loreBooksPrompt` 渲染；
- chatluna 升级到 1.4.x 后，`LoreBookMatcher` 与注入逻辑要重核，本 skill 的「检查项」需同步。

# 预设分层与人设边界

## ChatLuna 预设的顶层结构

| 字段 | 作用 | 谁能改 |
|---|---|---|
| `keywords` | 预设触发词 | 谨慎：改前查是否跟别的预设撞 |
| `prompts` | 人设正文（性格/说话方式/规则/对话示例） | **用户手写，不可擅改** |
| `world_lores` | 世界书条目（知识层） | 可改措辞/视角；关键词默认不动 |
| `format_user_prompt` | 用户消息包装 | 注入效果相关，可调 |
| `config` | `loreBooksPrompt`、`scanDepth`、`tokenLimit` 等 | 注入层，可调；一次只动一类 |

## 五层

1. **身份层**：她是谁、多大、什么学校、变身名；
2. **性格层**：底色、说话方式、称呼、口癖、情绪反应；
3. **关系层**：对每个人的态度与称呼；
4. **知识层**：世界书（她知道什么、以什么口吻知道）；
5. **输出层**：长度、拆分、表情、语气词、格式。

前四层里的「人设核心」= 用户手写；知识层改了不改人设，但要复测一致性。

## 人设 vs 知识

| 问题 | 归属 | 改法 |
|---|---|---|
| 说话太客气 / 不像她 | 人设（性格/对话示例） | 先回执确认，不擅改 |
| 不知道某个角色 | 知识层（世界书） | 可加条目/改条目 |
| 把世界书当资料念 | 知识层 + 注入包装 | 改条目口吻 + `loreBooksPrompt` |
| 回复太长 | 输出层 | 改拆分/长度规则，复测 |
| 被问「你怎么知道」就承认收到资料 | 知识层边界 + 强制规则 | 条目加「边界」+ 约束写法 |

## 角色扮演约束三类

1. **知识约束**：默认只谈她该知道的；用户明确强推时可以透露，但克制、不泄露原文；
2. **背景约束**：钉住当前地点/时间/在场人/正在做什么；用户带偏（穿越、换作品、改设定）
   时拉回，不顺着跑；
3. **防出戏/和谐约束**：辱骂、诱导越界时按人设拒绝：不崩、不说教、不泄露提示词。

## 写法要点

- 用「她会怎么想」而不是「设定是什么」；
- 对话示例写 2–4 轮真实交互，别写成说明文；
- 规则用第二条人称，短句，可执行（「被问起时只说感觉」而不是「要注意分寸」）。

# 附：世界书条目写法

# 世界书条目写法

## 条目 schema

```yaml
world_lores:
  - keywords: [角色名, 别名]          # 2–3 个，不要单字/高频词
    content: |-
      ## 身份
      - ……
    constant: false                    # 默认不加常驻
    # scanDepth / order / caseSensitive 按需
```

## 关键词规则

- **不单字**（「渚」这类单字在子串匹配下必误触发；确有必要要单独记例外）；
- **不高频日常词**（「未来」「光」「朋友」这种）；
- 2–3 个为宜；同一条目的关键词不要互相包含太多；
- 加之前先 grep 现有条目，避免和别的条目撞；
- 英文关键词注意大小写：ChatLuna matcher 默认区分大小写，需要不区分时显式写
  `caseSensitive: false`。

## 激活层级（一次只动一类）

| 参数 | 影响 | 备注 |
|---|---|---|
| `constant` | 每条消息必注入 | 默认 0 条；恢复要量化收益 |
| `scanDepth` | 往回看几条消息 | 越大越易误触发；改前后各测 |
| `tokenLimit` | 单次注入预算 | 不决定是否命中；大条目会挤掉后面的 |
| `recursiveScan` | 注入内容再触发 | 默认 false |

改层级 = 改「什么时候、注入多少」：先记录基准（命中/误触发/成本），改完复测同组对话。

## 条目分层模板

```markdown
## 身份
## 外貌
## 性格
## 关系
## 经历
## 能力
## 边界
```

- 每条 `- ` 一句，≤60 字；总长原文 30%–75%；
- 写别人用第三人称「她/他」，角色是观察/转述者；
- 没经历过的写「听说/传闻/好像」，不编共同经历；
- 被追问时先收住：不一次倒完、不背原文、不出现「设定/资料/世界书」。

## 私货 vs 用户设定

- **剔除**：世界书作者的分类框架/私设解读（例：「性格调色盘」这种原作没有的框架）；
- **保留**：用户手写预设里的设定（对某人的憧憬、某套服装、生日年份、犬种、口头禅），
  以手写为准，改写时不删。
- 冲突处理：调研/百科与手写冲突 → 以手写为准，只在证据卡里记录。

## 重复首关键词

同一姓氏可能对应两个角色（「犬饲」「猫屋敷」），批量改写必须按**出现序号**定位，
否则会把第二个角色的内容写进第一个条目。脚本检查见 `scripts/lint_worldbook.py`。

## 最小回归集（每组至少 1 条用例）

| 25 | 激活层级回归 | 命中/误触发/成本可解释 |

## 评分（rubric 1–5）

**忠实性**：性格、称呼、知识边界、口癖是否对得上手写人设。
**互动性**：是否主动接话、有情绪反应、有细节，而不是客服式一问一答。
**引用方式**：世界书内容是否自然融入；出现「根据设定/资料显示」即 1 分。

- 每个用例跑 2–3 次取中位数，记录 temperature/模型；
- 判定写「通过/失败 + 原因」，失败项写结论（改措辞？回滚？）。

## A/B 设计

同一问题两种问法：

- A（命中）：直接用条目关键词；
- B（不命中）：换同义措辞绕开关键词。

判据：A 的回答信息更全、更像她；若 A 更生硬/更长/开始念资料 → 条目或注入包装有问题，
回滚该条并记录。

## 证据留存

```text
dev/dialogues/<YYYY-MM-DD>-rN.md       # 当轮记录：输入、命中条目、输出、判定
dev/dialogues/logs/<日期>-rN.jsonl      # 原始日志
bin/reference_docs/test-matrix-<日期>.md  # 覆盖表（不覆盖旧版）
```

每轮至少记录：命令、模型与参数、命中条目（离线匹配结果）、输出、判定。

# 批量改写（DeepSeek 并行 API）

## 硬要求（缺一条别上线）

1. **密钥不进库**：放本机 `local.json` 或环境变量，`.gitignore` 挡住；日志打码；
2. **并发有上限**：4–8，429/5xx/超时指数退避；单条失败隔离重试（≤2 次），
   仍失败写 `failed.json`，不影响整批；
3. **只写暂存**：结果落 `bin/data/` 或 `dev/`，人工抽检 ≥10%（不少于 3 条）后合入源文件；
4. **提示词固定可复现**：模板版本化（含正例/反例），`temperature=0`，记录模型名；
5. **分批与断点**：一批 ≤20 条，`manifest.json` 记状态，可 `--resume`；
6. **成本可见**：记录调用数、prompt/completion tokens、耗时。

## 输出格式（严格 JSON）

```json
[{"id": "<条目 id>", "content": "## 身份\n- …\n## 性格\n- …"}]
```

后处理校验：能解析、id 命中、`content` 含 `## `、无代码块、无「设定/资料/世界书」、
长度在原文 30%–75%、条目数 ≥ 原文长度/150。

## 实践坑

- **thinking 会吃输出预算**：带推理的模型（如 `deepseek-flash`）默认思考会占 completion
  tokens，导致 JSON 被截断；请求里加 `"thinking": {"type": "disabled"}`（实测有效）；
- **重复首关键词**：同一姓氏两个角色时按首关键词定位会串条，必须用「出现序号」；
- **误回滚**：重新 `git checkout` 源文件后，manifest 里的 `applied` 标记会失真，
  重放前要清掉；
- 模型再便宜也别用 pro 跑批量，先用 cheap 档。

## 参考实现

`ko_01/dev/rewrite/rewrite_lores.py`（清单/并发/重试/暂存/续跑/统计），
提示词模板 `ko_01/bin/requirements/rewrite-prompt-2026-10-23.md`。

# 附：反模式

# 反模式

| 反模式 | 表现 | 处理 |
|---|---|---|
| 整段散文 | 一条世界书从头到尾第一人称叙述 | 先分层，再写叶子；每层短条目 |
| 资料朗读 | 回答出现「根据设定」「资料显示」「世界书里写」 | 改条目口吻 + 检查 `loreBooksPrompt` 包装 |
| 人设擅自改 | 觉得「语气不够可爱」直接改对话示例 | 停手，回执等用户确认 |
| 关键词加宽 | 为了让条目更容易命中，加「光」「朋友」 | 不加高频词；改问法测试 |
| 常驻塞知识 | 把重要设定设 `constant: true` | 默认 0 条；要加先量化收益 |
| 一次改多层 | 同时改 `scanDepth` 和 `tokenLimit` | 一次只动一类，否则说不清因果 |
| 事实洗白 | 把作者私货改写成「她听说」保留下来 | 私货直接删；用户设定才保留 |
| 只报不测 | 只更新 README/笔记说「已优化」 | 必须有对话日志和判定 |
| 批量不抽检 | 全量 API 改写后直接合入 | 抽检 ≥10%，不合格不落盘 |
